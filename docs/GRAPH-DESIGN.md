# Graph design: one relation registry over the existing id spaces (PRE-REGISTERED)

Status: DESIGN ONLY. No code in this round. The implementation round locks its
acceptance criteria from section 7 BEFORE it starts.

## 1. Problem

Five id spaces already exist and are individually fine:

| Space | Shape | Source of truth |
|---|---|---|
| milestones | `M1..M6` | docs/PRD.md, docs/evidence/milestones.json, data/milestone-plan.json |
| work units / tasks | `W1..W18` (demo also `t*`, `p*`) | plan work_units, SQLite tasks |
| issues | `I-001..I-019` | docs/evidence/issues.json |
| PDCA entries | `C4..C11`, `R17..R24` (two hand-named series) | docs/TASK-LOG.md |
| handoffs | `G1..G3`, `C9-P1/P2` | docs/handoffs/ |

Edges exist in three places only: `milestone-plan.relations` (W to W, with
FS/SS/FF/SF + lag), SQLite `task_deps`, and `parent_id` (the tree). The
relations BETWEEN rounds and everything else — rework-of, scope, fixes — live
in prose ("rework-of: R17"), so no machine can walk the graph. That is the
whole defect. The ids are readable and unique per space; converting them to
UUIDs would destroy readability and fix nothing.

## 2. Design

One registry file, `docs/evidence/relations.json`, plus one machine line in
every future PDCA entry header. Existing ids are reused as node ids.

### 2.1 Node kinds

`milestone | task | issue | entry | handoff`

A node id is globally unique WITHIN its kind; edges always name both endpoints,
so cross-kind reuse (none exists today) stays unambiguous.

### 2.2 Edge types

| rel | from -> to | Payload | Source today |
|---|---|---|---|
| `contains` | milestone -> task | — | milestone-plan work_units[].milestone_id |
| `depends` | task -> task | `type` (FS/SS/FF/SF), `lag` | milestone-plan.relations, SQLite task_deps |
| `parent` | task -> task | — | SQLite parent_id |
| `scope` | entry -> milestone or task | — | NEW: PDCA machine line |
| `rework-of` | entry -> entry | — | NEW: PDCA machine line |
| `fixes` | entry -> issue | — | NEW: PDCA machine line |

Direction convention: edges read "from depends on / belongs to / repaired to".
`depends` direction matches `task_deps` (from_id reaches to_id).

### 2.3 PDCA machine line (the integration point)

Every NEW entry in docs/TASK-LOG.md carries ONE machine line directly under its
heading, before P:

    Graph: scope M4/W10 | fixes I-018 | rework-of C7

Rules:
- `scope` is MANDATORY for every new entry. One entry scopes to exactly one
  plan node (a milestone or a task). This is how a PDCA round attaches to the
  PRD iteration loop: the round finishes, `plan-sync --set` writes status back
  by that id, and the scope edge records the attachment.
- `fixes` and `rework-of` are optional, repeatable (`fixes I-017,I-018`).
- Multi-scope is forbidden at v1. A round that touches two nodes splits into
  two entries. (Revisit only with evidence from real use.)
- Old entries are NEVER edited (append-only). Their edges go through the
  backfill map below.

### 2.4 Registry shape

```json
{
  "schema": "ai-project-ops.relations/1.0",
  "generated_by": "scripts/graph.js --build",
  "nodes": [ { "id": "M4", "kind": "milestone" } ],
  "edges": [ { "from": "W10", "to": "W11", "rel": "depends", "type": "FS", "lag": 0 } ],
  "backfill": [ { "from": "C10", "to": "C7", "rel": "rework-of",
                  "source": "TASK-LOG C10 Act line (manual map, R25)" } ]
}
```

- `nodes` and `edges` are HARVESTED deterministically from the three live
  sources plus the machine lines. The build is idempotent and ordered.
- `backfill` is the ONLY hand-maintained block. Every entry names its source
  text. The build merges backfill into the graph after harvest.
- The file is committable evidence. It is regenerated by `--build`; drift is a
  FAIL of `--check`, never silently overwritten.

### 2.5 CLI contract (future `scripts/graph.js`, Node, zero deps)

    node scripts/graph.js --build      # rewrite relations.json from sources
    node scripts/graph.js --check      # exit 0 clean / exit 2 on FAIL lines
    node scripts/graph.js --query <id> # print every edge touching <id>

`--check` failures (each prints a `FAIL` line with the offending id pair):
1. dangling endpoint: an edge names a node that no source defines;
2. dependency cycle in the `depends` + `parent` union (recomputed, not
   inherited from write-time guards);
3. a NEW entry (dated after this design) with no `Graph:` line;
4. a `Graph:` line naming a node that does not exist;
5. registry drift: relations.json differs from a fresh `--build`.

`--query W10` prints: contains / depends / parent edges from the live sources,
plus every entry that scoped to it, fixed an issue blocking it, or reworked a
round that scoped to it. One screen, no pager.

### 2.6 Gate wiring (future invariant I11)

`scripts/discipline-gate.js` gains I11 (HARD): `node scripts/graph.js --check`
must exit 0. Negative control enters `scripts/selftest-discipline.js`: inject a
dangling edge and a missing machine line into a temp tree, assert exit 2 for
each. A gate that never fires is decoration.

## 3. How this closes the PDCA <-> PRD loop

1. A round opens: its entry header declares `Graph: scope M4/W10`.
2. The round does the work; Check carries real evidence (unchanged discipline).
3. Status propagation uses the SAME id: `plan-sync --set W10:done:100`.
4. The scope edge lands in the registry, so the plan node now knows which
   rounds touched it, in order, with evidence links (the ledger entry ids).
5. A later repair round declares `Graph: scope W10 | rework-of C12`, and the
   redo chain becomes walkable instead of prose.

The graph is therefore an INDEX over facts that already live in the plan, the
database and the ledger. Per section 7 discipline: facts live in docs and
SQLite; the registry never becomes a source of truth for anything it indexes.

## 4. Non-goals (locked)

- No UUID renumbering. Existing id spaces stay as they are.
- No panel / gantt UI change in the core round. A query command is enough;
  any visual view is a separate later round with its own acceptance.
- No edits to existing TASK-LOG entries. Backfill map only.
- No new npm dependency. Node stdlib only, matching the package rule.
- No change to the data contract (handoff filenames and field names).
- No re-run of the C4 effectiveness experiment; this is structure, not
  effectiveness evidence.

## 5. Open questions (decide at implementation time, with evidence)

- Does `--build` read SQLite `task_deps` live (requires panel.db) or from a
  seeded export? Follow the C10 three-state pattern: SKIP when absent, never
  implicit create.
- Should `entry` nodes also index handoff files (`produced` edge)? Cheap, but
  defer until a query needs it.
- Does the backfill map belong inside relations.json or in a sibling file?
  Start inside; split only if merge conflicts appear in real use.

## 7. Acceptance criteria for the implementation round (LOCK before work)

1. `node scripts/graph.js --check` exits 0 on the committed tree.
2. Every source edge is represented: count(contains) = count(plan work_units),
   count(depends) = count(plan relations) + count(task_deps rows when
   panel.db present), count(parent) = count(parent_id rows non-null).
3. Every PDCA entry dated after this file carries a `Graph:` line naming an
   existing node; `--check` proves it (FAIL line otherwise).
4. Negative control: dangling edge and missing machine line each produce
   exit 2 in `scripts/selftest-discipline.js` (which grows additively).
5. `templates/pdca-entry.template.md` carries the machine line slot.
6. Backfill covers the pre-design entries that state rework/fix relations in
   prose (C10 -> C7 rework-of at minimum), each with a `source` note.
7. All shipped gates stay green: validate_skill 14/14, localize CJK_COUNT=0,
   selftest-discipline 15/15 + new, verify.js 111/111 + new, discipline-gate
   PASS including I11.
8. Scored PASS only with pasted evidence per the TASK-LOG discipline.
